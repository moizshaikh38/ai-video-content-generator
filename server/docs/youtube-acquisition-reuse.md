# Original bounded YouTube acquisition reuse

This adds optional reuse of completed small MP4 acquisitions. It is not audio-first analysis, overlapping-range assembly, a new extraction provider, active-live capture, a proxy/cookie change or a deployment.

The cache is consulted only after the existing fresh metadata preflight admits a matching video ID and positive duration. Existing terminal access/live/age/region failures remain authoritative. An unavailable metadata response cannot clear reuse. The key includes user, video, exact requested interval, current reported duration and acquisition format profile. Full-source and range acquisitions never alias, nor do different users or profiles. This preserves the existing selected-range timeline contract rather than concatenating unrelated ranges.

Stored bytes are verified after the normal decoder probe. Each reuse verifies SHA-256, length, version, timestamp, key and file type, then creates a caller-owned private temporary copy and verifies it again. The ordinary decoder probe, per-project object upload/persistence and cleanup still run. Cache failures are misses, not import failures. A changed reported duration invalidates reuse; an in-place source edit preserving ID and duration is not detected by metadata, so this is short-lived reuse of a recorded acquisition, not proof of current byte identity at the provider.

Conservative limits: 32 MiB per entry, at most four completed entries, one-hour reuse validity, at least one GiB available disk after a copy, private directory/file modes, no symlink roots/entries and a cross-process writer lock. Lock contention or a stale writer lock skips cache insertion rather than overriding it. Larger imports continue ordinary acquisition. Expired entries are removed on later insertions, not on a new background schedule; unused cache files can remain on disk after their reuse validity expires. No persistent provider cookies, tokens or signed media links are stored in the receipt.

Qualification at first implementation: filesystem tests and actual local fixture repeated ingestion exercise hash verification, isolation, ranges, expiry, no-admission behavior and project/object creation. Provider metadata/first acquisition are mocked for that fixture; these tests are not a fresh external YouTube acquisition or a reliability/speed benchmark. A known earlier server YouTube bot challenge is not fixed by this cache. Do not retry challenges or enable external/paid services to manufacture a pass.

Future audio-first work must first separate transcript analysis from video-dependent scene/framing measurements and preserve source-time mapping. Future range reuse needs proof of coverage, quality, interval origin and frame-accurate assembly, not just filename similarity. Neither is silently claimed by this change.

A permanent opt-in local integration regression is `server/src/tests/youtubeAcquisitionRecovery.test.ts`. It generates a small synthetic video/tone, deliberately refuses the first loopback object upload, verifies no project was created, then verifies same-range reuse without another acquisition and a changed-range cache miss. Set `YOUTUBE_CACHE_TEST_MONGODB_URI` to an isolated loopback Mongo URI; the test uses a fresh uniquely named database, deletes only that database and its generated media, and refuses non-loopback or credential-bearing URIs. Without the variable it is explicitly skipped. Run it through the installed TypeScript test loader with the normal resource guard. The test mocks YouTube metadata/acquisition, not the decoder, local upload or Mongo persistence. It is not live-provider qualification.
